# DBHub 语句门禁（Gate）分级策略设计

两个查询入口——**人** 和 **AI Agent**——都必须走同一套安全策略，但两者的"档位"不同。
命令按危险度分三档；每个数据库（**含 Glue**）在全局默认之上还能维护自己的命令清单。

有一处静态文本分类做不到的事（§5 的"删部分行 vs 删整表"），我在那里如实说明并给出可落地
的近似，其余按已定的模型落。

## 1. 两个入口，两套 actor 策略

安全决策 = **谁在执行（actor 策略）** × **执行什么（命令档位）**。先定 actor。

### 1.1 人：只有一个"可写"开关

| 开关 | 关（默认） | 开 |
|---|---|---|
| **可写** | 改数据类命令一律拒 | 改数据类命令**弹确认**后跑 |

- 人是这套系统里的**最终权威**：可写打开后，连"拒绝档"（DROP 整表）也能由人执行——
  只是要过一道更重的确认。AI 的"拒绝档"正是**交给人**来做的（§1.2）。
- **不再单设"可读"开关**（决策 5）：可读是连接的常态，要停用它就取消"显示为标签页"，
  不必再引入一个只表达"暂时别查"的开关。少一个开关就少一处状态组合要推理。
- 映射既有字段：`allow_writes` 直接成为"可写"开关，无需新字段。

### 1.2 AI Agent：是否启用 + 三档模式

第一道门是既有的 **`enabled_for_ai`（是否启用 AI 访问）**——不启用就没有 AI 工具，与档位
无关。启用后由模式决定 AI 能做什么：

| 模式 | 只读命令 | 改数据命令 | 拒绝档命令 |
|---|---|---|---|
| **观察者**（默认） | 直接跑 | 拒 | 拒 |
| **确认** | 直接跑 | **弹给用户确认** | 拒（交给人） |
| **自由执行** | 直接跑 | 直接跑（**v1 暂不开，见决策 1**） | 拒（交给人） |

两条贯穿始终、不受模式影响的铁律：

1. **"拒绝档"对 AI 永远是拒**，无论哪种模式——包括"自由执行"。DROP 整表这类操作
   AI 不自己做，是交给人（§1.1 的可写人）。你的原话"通常是直接拒绝执行,将执行交给人"
   我把"通常"落成"总是"，因为一旦留口子，注入攻击就会专门去找那个口子（§6）。
2. **AI 的改数据能力受人封顶**：人要先把这个连接的可写打开，AI 才可能在改数据档上动作。
   取 `min(人策略, AI模式)`。否则 AI 会成为绕过人开关的旁路。

映射既有字段：把 `DbReadOnlyPolicy` 从单变体扩成 `Observer | Confirm | Free`；
`SelectOnly` 等价于 `Observer`，可平滑迁移。`enabled_for_ai` 保持不变，继续做那第一道门。

## 2. 命令三档 + 每库自定义清单

### 2.1 三档（这是"执行什么"那一维）

| 档 | 含义 | 典型命令 |
|---|---|---|
| **A 自由**（Allow） | 只读、确认安全 | `SELECT`(无`INTO`)、`SHOW`、`DESCRIBE`、`EXPLAIN`、`USE`、`WITH…SELECT` |
| **B 确认**（Confirm） | 改动**部分**数据 | `INSERT`、`UPDATE … WHERE`、`DELETE … WHERE`、`MERGE`、`CALL` |
| **C 拒绝**（Refuse） | 结构级 / 全表级 / 权限级破坏 | `DROP`、`TRUNCATE`、`ALTER`、`RENAME`、无 `WHERE` 的 `DELETE`/`UPDATE`、`GRANT`、`REVOKE`、`SET`、`KILL`、`LOAD` |

档位是**语句自身的属性**，A/B/C 对人和 AI 是同一套划分；不同的只是每个 actor 在每档上
的动作（§3 的矩阵）。

### 2.2 每个数据库的自定义清单

全局默认给一套 A/B/C 划分。**每个连接**（含 Glue 这个内置源）可维护自己的覆盖清单：

```jsonc
// 连接上的 gate_policy 列（JSON）
{
  "human": { "write": false },
  "ai":    "observer",                 // observer | confirm | free
  "overrides": {                       // 只写"和全局默认不同"的命令
    "CALL":            "refuse",       // 这个库的存储过程一律不许 AI 碰
    "TRUNCATE":        "confirm",      // 这是个 staging 库，清表是日常
    "sp_rebuild_index":"allow"         // 指名某个过程为安全
  }
}
```

- 覆盖的粒度是**命令关键字**或**具名对象**（存储过程名等），不是开放正则——正则清单最终
  没人敢改也没人看得懂，且每条都是新的绕过面。
- 缺列 / 解析失败 → 回落到**全局默认**，绝不回落到"全开"（§7 不变量）。
- 覆盖只能在全局默认之上**逐条挪档**，不能新增"匹配方式"。

## 3. actor × 档位 决策矩阵

这是全设计的中心。把 §1 和 §2 合起来：

| | A 自由 | B 确认 | C 拒绝 |
|---|---|---|---|
| **人 · 可写关** | 跑 | 拒 | 拒 |
| **人 · 可写开** | 跑 | 确认后跑 | **重确认**后跑 |
| **AI · 观察者** | 跑 | 拒 | 拒 |
| **AI · 确认** | 跑 | 确认后跑 | 拒（交给人） |
| **AI · 自由执行** | 跑 | 跑（v1 暂不开） | 拒（交给人） |

读法：先按 actor 选行，再按命令档选列，交叉格就是动作。"人·可写开"这一行是唯一能落到
C 档还执行的——因为人是把 AI 拒掉的那些操作接手的人。

前置门：AI 的三行都还要先过 `enabled_for_ai`（§1.2 第一道门）；人则要先"显示为标签页"。
"AI · 自由执行"的 B 档在 v1 里**当作"拒"**处理（决策 1），表里写"跑"是它的目标语义。

### 3.1 "交给人"具体是什么

AI 落到 C 档（或观察者/确认模式下落到被拒的档）时，不是静默失败，而是返回**结构化拒绝**，
说明：命令档位、为什么拒、以及"这类操作需要人在查询页手动执行"。Chat 把它呈现给用户，
用户可以到该连接的查询 tab 自己跑（走"人·可写开"那一行）。

### 3.2 批量语句：取最严的一条

一段 SQL 里多条语句时，**整批按批内最严的那条定档**：任一 C → 整批按 C；否则任一 B →
整批按 B。确认弹窗**必须点名**是哪一条触发的，不能让用户在一大段脚本里自己找。

### 3.3 必须承认的后果：确认放行 = 少一层防线

`query.rs` 今天的 `writable` 是**整次运行一个布尔**（`query.rs:150`）。确认档一旦放行一条
改数据语句，这次运行就得以可写会话打开，**意味着第二层防线（JDBC 只读会话）对这条语句
失效，只剩门禁一层**。所以：

- C 档的默认集合要保守（§4 就是）。
- 实现上 `execute()` 的入参要从 `bool writable` 改成携带完整决策的结构
  （`GateDecision { tier, action, matched }`），由调用点算好传入，杜绝"先判后传"两处不一致。

## 4. 默认配置

新连接、缺列、解析失败都落到这套全局默认。**关键：这套默认对人的行为与今天完全一致**
（人默认可写关 = 今天 `allow_writes=false`），升级不悄悄放宽任何人的边界。

**命令 → 默认档**：

| 命令 | 默认档 | 理由 |
|---|---|---|
| `SELECT`/`SHOW`/`DESCRIBE`/`EXPLAIN`/`USE` | A | 查询页主用途 |
| `SELECT … INTO` / `INTO OUTFILE` | C | 形似读实为写文件 |
| `INSERT` / `UPDATE…WHERE` / `DELETE…WHERE` | B | 改部分数据，可确认 |
| `DELETE`/`UPDATE` **无 WHERE** | C | 全表改动，见 §5 |
| `DROP` / `TRUNCATE` / `ALTER` / `RENAME` | C | 结构级、不可撤销 |
| `CALL` / `EXECUTE` | B | 过程内部对分类器不可见，给确认而非放行 |
| `GRANT`/`REVOKE`/`SET`/`KILL`/`LOCK`/`LOAD` | C | 权限/会话级，影响面超出单句 |
| **不认识的首词**（Unknown） | **C** | 见下 |

**actor 默认**：人 = `{ write: false }`（可读不设开关，决策 5）；AI = 未启用；启用后模式为
`observer`。

**Unknown 默认为 C（拒绝）而不是"确认"**：一条分类器都认不出的语句，用户通常也判断不了
（可能是几百行脚本或把危险藏在中段）。把"不认识"默认设成确认，等于把门禁从 fail-closed
改成 fail-open。想放宽的库可以在 §2.2 的覆盖里把 `unknown` 挪成 `confirm`，但那是显式选择、
且要在 UI 上说明代价。

## 5. 分类器的能力边界

### 5.1 一条静态分析画不准的线：删部分 vs 删整表

你把"`update`/`delete` **某一些**数据"划到确认档、"`DELETE` **整个表**"划到拒绝档——这个
区分是对的、也是重要的，但**门禁是首词 + 文本匹配，不解析 SQL**，所以这条线只能近似：

- `DELETE FROM t`（无 WHERE）= 删全表 → 能靠"**没有 WHERE**"识别，划 C。✅
- `TRUNCATE t` / `DROP TABLE t` = 必然全表/整表 → 首词就能定，划 C。✅
- `DELETE FROM t WHERE id = 3` = 删部分 → 有 WHERE，划 B。✅
- `DELETE FROM t WHERE 1 = 1` = **实际删全表，但有 WHERE** → 会被划成 B（确认）。❌

最后一条是这套近似的**已知盲区**：`WHERE 1=1`、`WHERE true` 这类恒真条件删的是全表，却带着
WHERE，静态文本判不出来。要精确必须上真正的 SQL parser + 常量折叠，那是另一个量级的工程。

**设计取舍**：v1 用"有无 WHERE"做启发式（无 WHERE 的 `DELETE`/`UPDATE` 升到 C），并**如实
告诉用户这是启发式**——确认弹窗上写明"这条语句会改动数据，具体影响多少行本工具无法确定"。
真正的兜底仍是 §3.3 说的"C 档保守 + 人是最终权威 + 全量审计"，而不是假装分类器能算准行数。

### 5.2 分类器已修（决策 2，**已实现**）

`gate.rs` 的写入关键字审计原先是对**整段原始文本**做带空格子串匹配，两个方向都有 bug：

- **误报**：字符串字面量里的关键字被当成代码。`where note = 'please DROP this row'` 含
  ` DROP `，于是**存放 SQL 文本的表（模板表）根本查不了**。
- **漏报**：关键字紧挨标点就漏掉。旧检查要求两侧各有一个空格，所以拿换行顶替那个空格时
  `SELECT * INTO\nOUTFILE '/tmp/x'` **直接放行**——这是一个真实的绕过。

已改成读取语句的**代码 token**：跳过字符串字面量、引号标识符与注释，再按**整词**匹配
（`INTO(` 能命中，`into_backup` 不会）。新增 7 个测试覆盖两个方向，`gate::` 19 个测试、
全量 Rust 456 个测试通过。

两个刻意的取舍，写在这里备查：

- **`SELECT … FOR UPDATE` 现在被拒**。它以前是靠 `strip_comments` 在行尾补的 `\n` 才漏过
  检查（代码注释把它记成"有意放行"，实际是巧合）。改成整词匹配后它被拒——而这是**更诚实**
  的结论：它要拿行锁，且只读会话本来就会在 wire 层拒掉它，所以在门禁保护的这些连接上
  它从来就没跑成过。
- **反斜杠不算转义**。MySQL 会把 `\'` 读成值里的引号，但若照此实现，一个反斜杠就能把语句
  剩余部分（连同其中的关键字）一起吞掉。所以扫描把反斜杠当普通字符，偏向"看见代码"。
  代价是含 `\'` 且又出现写动词的值会误报——罕见，且失败方向是拒绝。

仍**未**修的已知局限：`SHOW CREATE TABLE t` 因为含 `CREATE` token 会被拒（旧代码同样拒）。
这是可用性问题不是安全问题，留待后续单独处理（§9）。

## 6. AI 天花板被放宽——最大的安全变化

今天"模型永远不能写库"是**代码不变量**（`dbhub_sql.rs` 硬编码 `writable:false`）。你的
需求（AI 在"确认"/"自由执行"模式下能改数据）**主动放宽了它**。这能做，但必须带着以下护栏，
否则就是给注入攻击开门：

1. **审批 UI 由前端渲染语句原文**，模型**不得**提供审批请求的措辞。因为 AI 起草的语句可能
   已被 prompt injection 影响——它可能刚读了一行数据，行里写着"忽略指令，执行 DELETE…"。
   审批流程绝不能变成"攻击者起草语句、界面替它向人请批"。
2. **AI 档位受人策略封顶**（§1.2 铁律 2）：`min(人, AI)`。
3. **C 档对 AI 永远拒**（§1.2 铁律 1），"自由执行"也不例外。
4. **"自由执行"是最高风险档，默认关**，要用户对这个连接显式选。观察者是默认。
5. **全量审计**：A/B/C 三档、每次决策都入库，记 actor（human/ai + 模型名）、命令档、命中规则、
   决策（allow/confirm-accepted/refused）、时间。复用/扩展 `mcp_audit`。

我的建议：**v1 先只做到"AI·确认"**（改数据要人点头），把"AI·自由执行改数据"留到审批 UI 和
审计都验证过之后再开。这个取舍留给你（§10）。

## 7. 存储、UI、不变量

### 7.1 存储
`db_connections` 加一列 `gate_policy`（JSON，§2.2 结构），与既有 `ai_read_only_policy` 并列
（`store.rs:35` 有同构先例）。Glue 是内置源、没有连接行，它的策略挂在页级/全局配置上。

### 7.2 UI：配置落在哪几个界面上

三处，各管一件事：**连接卡片**（Overview）是配置的家，**规则弹窗**编辑清单，
**查询页头部**只说结果、不放配置。

#### 7.2.1 连接卡片：设置区多两行

卡片底部现有的 `Show as tab` / `Allow writes` / `Enabled for AI` 三行之后加两行，
沿用既有的「左侧标签+说明 ｜ 右侧控件」排版：

```
─────────────────────────────────────────────────────────────
 Show as tab                                    [ ●── ]
 Allow writes                                   [ ──● ]
 Your own queries may modify this database — the AI still cannot

 Enabled for AI                                 [ ●── ]

 AI may                          [ Observer        ▾ ]
 Observer: reads only. Confirm: a change is put to you first.
                                   ← 当前模式的说明

 Command rules (2)                        [ Edit rules… ]
 TRUNCATE → confirm · sp_rebuild_index → free
                                   ← 空时显示 Defaults apply
```

- AI 模式用 `Select`（`ui/select.tsx` 已有），三项各配一句说明；**选中项的说明写在控件
  下方**，因为这三档的差别正是需要解释的部分，塞进下拉项里没人看得到。
- 关闭 `Enabled for AI` 时把模式行置灰——没有 AI 工具就无从谈起模式。规则行**不**置灰：
  它们同样作用于人自己的查询（已接线）。
- 规则行只给摘要 + 入口。清单本身太长，卡片上放不下，也不该在卡片上编辑。

#### 7.2.2 规则弹窗：`ConnectionRulesDialog`

沿用 `DeleteAccountDialog` / `DbAnalyzeDialog` 的形态（`ui/dialog.tsx`），标题写明
是哪个连接的规则：

```
┌ Command rules — Sales MySQL ────────────────────────────────┐
│ 未列出的命令按默认档执行。                                    │
│                                                             │
│  命令              作用范围            档位        操作       │
│  ─────────────────────────────────────────────────────────  │
│  TRUNCATE          所有 TRUNCATE      [Confirm ▾]   [×]     │
│  sp_rebuild_index  仅 CALL 此过程      [Free    ▾]   [×]     │
│                                                             │
│  [ + 添加规则 ]                                              │
│                                                             │
│  档位：Free 直接执行 · Confirm 需你确认 · Refuse 拒绝         │
│                                                             │
│  [恢复默认]                              [取消] [保存]        │
└─────────────────────────────────────────────────────────────┘
```

**「作用范围」这一列是这个界面存在的理由，不是装饰。** 门禁对键的匹配是窄的（§2.2）：
键**等于某个动词**时作用于该动词的全部语句；键**不是动词**时只作用于「CALL 这个名字」——
`DROP TABLE sp_x` 不会因为它而放宽。用户看不见这条规则，就会写出「以为自己放宽了、
其实没有」（或反过来）的配置。

由此三条：

- **键不让人自由乱填。**「添加规则」给一个组合框：选动词（固定清单，来自 `tier_for_verb`
  的键），或选「一个存储过程」并从目录树挑名字。手打的自由文本会产生**永不生效的死规则**
  （键既不是动词，也不对应任何过程调用）。
- **作用范围由键推出来并显示**，不给用户选——它不是配置项，是匹配规则的后果。
- **默认档要看得见。** 弹窗里放一张紧凑的默认档对照（至少覆盖常见动词），否则用户是在
  盲改一个自己没见过的默认。

#### 7.2.3 查询页头部：不放配置

头部的状态图标保持只读/可写两态 + hover 说明，**不放 AI 模式**——那一行说的是「人自己的
查询」，AI 的模式与之无关，混进去只会让人以为它约束自己。

规则的影响通过**拒绝消息**抵达用户，而不是常驻徽章：被规则拦下时消息已经写成
`"TRUNCATE" is refused by this connection's rule for "TRUNCATE"`，在需要的那一刻说明原因，
比一个一直挂着的「有 2 条规则」有用。

#### 7.2.4 确认弹窗：「始终允许此类」不是哪里都能给

本节原先把「始终允许此类」写成确认弹窗的三个按钮之一。落地时它有一个硬约束：**这个按钮
要写回一条规则，而规则只能以「动词」或「过程名」为键。**

- `CALL sp_rebuild_index()` 被确认 → 可以写 `sp_rebuild_index: free`，作用范围正好。
- `DELETE FROM orders WHERE id = 3` 被确认 → **没有安全的键可写**。`DELETE: free` 会把
  整表删除一起放宽（而整表删除属 Refuse 档，本来就不该走到这条路径）；用表名做键又根本
  不匹配（名字键只对过程生效）。

所以第三个按钮**只在存在安全键时出现**（目前 = 过程调用）；没有安全键时只有
「取消 / 仅本次运行」。这不是偷懒，是这个覆盖模型能表达出的边界的诚实反映。

要让「这张表的删改以后都放行」成立，需要给覆盖模型加**表级键**（动词 + 表名），那是另一个
改动，记在 §10 的后续项里。

确认弹窗本身（人和 AI 共用组件）不变：语句全文（等宽可滚动、**前端渲染**）、命中档位与
规则、按 §5 的诚实措辞、批量时高亮触发条；超时/失焦/退出 = 拒绝。

### 7.3 不变量（无论怎么配都成立）
1. **默认拒绝**：无策略/解析失败/分类器内部错 → Refuse，绝不 Allow。
2. **批内取最严**。
3. **C 档对 AI 恒拒**，自由执行不例外。
4. **AI ≤ 人**：`min(人策略, AI模式)`。
5. **审批 UI 由前端渲染语句，模型不措辞审批请求**。
6. **全量审计**三档决策。
7. **无人应答 = 拒绝**。

## 9. 局限与不做

- **确认 ≠ 可撤销**：是执行前审批，不是两阶段提交。MySQL DDL 隐式提交，弹窗文案不能暗示可回滚。
- **门禁是文本分类不是语义分析**：`WHERE 1=1` 删全表这类判不准（§5），只能把误判方向控在保守侧。
- **方言差异**：A/B/C 的判定对 MySQL/Postgres/Yellowbrick 并不完全一致，精确需按 dialect 分派。
- **不做**：列/行级权限、按表粒度策略、SQL 重写/脱敏——另一个产品维度。
